# receiptly 家庭小票账本

**产品需求文档（PRD + 可验收需求）**  
版本：1.1（已完成十轮自审，补充多维聚合需求）｜更新日期：2026-07-21｜状态：可进入 UX / 技术设计

## 1. 结论与范围

receiptly 是一个先供单个家庭使用的私有账本：用户拍摄购物小票，系统用 AI 提取候选内容并自动建议分类；用户确认后，数据才进入家庭账本。家庭成员可以按任意时间段、商品、品类和超市查看实际支出，并基于**本家庭已确认小票**比较同一商品在不同超市的历史购买价。

首版目标是让一家人在 60 秒内完成一张普通小票的入账，并能回答：

1. 任意开始和结束日期内，我们家总共花了多少？
2. 在任意时间段内，钱主要花在哪些商品、品类和门店？这些商品按花费如何排名？
3. 某个商品在任意时间段内总共花了多少、买了几次？
4. 某个商品在 PAK'nSAVE、Woolworths、New World 等我们实际去过的店，所有历史购买价及其按店铺筛选后的价格分别是多少？
5. 哪些可解释的消费结构或节约机会值得留意？

### 1.1 产品原则

- **确认优先：** AI 提取和分类都是候选值；未确认的行项目绝不进入正式金额、价格比较或洞察。
- **家庭私有：** 不抓取、复制或公开展示零售商网站数据；比较仅来自本家庭自愿上传且已确认的小票。
- **可追溯：** 每个统计数字都能回到收据、日期、门店和行项目；价格结论显示样本数与可比性。
- **不越界：** 健康功能是中性的“购买结构提示”，不是医学、营养诊断、治疗、减重或儿童饮食建议。
- **手动可完成：** OCR、AI 或网络失败时，用户仍能完整创建和确认收据。

### 1.2 MVP 边界

| 包含 | 不包含 |
| --- | --- |
| 私有家庭、成员邀请、角色控制 | 公开商品数据库、公开跨超市排行榜 |
| 小票拍照上传、手动录入、AI 候选提取 | 抓取、爬取、镜像或再发布零售商内容 |
| 自动分类建议、用户修正与规则记忆 | 无确认的全自动入账 |
| 时间/商品/品类/超市支出统计 | 付款、下单、优惠券、返佣、广告 |
| 本家庭同商品的跨店历史实付价 | 宣称“市场最低价”“原价”或实时全网比价 |
| 单位价、促销可比性提示 | 自动跨规格等价或自动跨品牌替代结论 |
| 购买结构、预算和个人历史价提示 | 医疗/营养评分、疾病或饮食处方 |

## 2. 用户、角色与关键场景

### 2.1 角色

| 角色 | 权限 |
| --- | --- |
| 家庭所有者（Owner） | 创建家庭；邀请/移除成员；管理分类、商品别名、预算和洞察开关；导出及删除家庭全部数据。 |
| 家庭成员（Member） | 上传、编辑、确认和删除自己创建的收据；查看家庭已确认统计；可提出商品合并建议。删除已确认收据会影响家庭统计，须显示影响范围和二次确认。 |
| 系统服务 | 保存 AI 候选、运行统计和生成提示；不得将小票、商品文本或家庭行为用于广告、公开展示或模型训练。 |

Owner 可处理商品合并建议，并能编辑/删除任意家庭收据；成员不能直接合并会改变其他成员历史的家庭商品。第一版只有一个家庭所有者即可；成员邀请采用一次性、过期的链接或邮箱邀请。未加入前不显示任何家庭账本信息。

### 2.2 主要场景

1. 用户结账后拍一张 PAK'nSAVE 小票；系统读出日期、门店、合计和 18 行商品。用户改正两行、确认分类、提交。
2. 三个月后，用户搜索“Anchor 牛奶 2L”，查看自己家在各超市的购买次数、最近价、最低价和可比单位价。
3. 月底，用户选择 2026-07-01 至 2026-07-31，查看按类别支出和超过预算的类别；点击任一数字可查看其行项目。
4. 用户看到“零食占食品已确认金额 16%”的购买结构提示，查看覆盖率与包含的类别；它不评价任何人的健康。
5. OCR 无法读出皱折小票时，用户手动填门店、日期、总价和项目，仍可完成入账。
6. 用户选择任意日期范围，按“商品”分组并按总花费降序排序，得到这段时间花费最高的商品排名；切换为“门店”或“类别”后，使用同一筛选条件重新聚合。
7. 用户搜索某个家庭商品，选择“全部历史”或任意日期范围，并可只看一个门店或所有门店的每次购买价格与汇总。

## 4. 核心流程与功能需求

### 4.1 收据创建与 AI 提取

**FR-REC-01：** 用户可从相机、相册或桌面文件上传一张 JPG、PNG、HEIC 或 PDF 小票。上传前展示文件类型、大小和清晰度说明；超过产品配置上限或无法解码时拒绝并给出手动录入入口。

**FR-REC-02：** 系统为每张上传创建 `draft` 收据和私有原图；原图不得通过猜测 URL 访问。上传过程中显示进度，可取消；失败后保留本地草稿及重试选项。

**FR-REC-03：** AI/OCR 仅生成候选：门店名称、交易日期/时间、币种、合计、税费/折扣、行项目原文、数量、单价、行价、包装规格与类别。每一字段保存置信度和原始文本；系统不得把候选直接当作事实。

**FR-REC-04：** AI 失败、超时或置信度低时，显示“未能可靠读取，请手动填写”，而不是虚构或静默填充数据。手动路径必须可添加/删除/排序行项目、填写门店/日期/合计与类别。

**FR-REC-05：** 系统识别到同一家庭中相同门店、日期、合计且原图哈希相同/相近的小票时，显示“可能重复”；用户可取消、继续另存或打开已有收据。系统不得自动删除。

### 4.2 确认、分类和商品规范化

**FR-CON-01：** 确认页按行展示“原始小票文本 → 可编辑显示名称、数量、规格、实付行价、类别、促销标记”。用户可以逐行确认、批量修改类别，或移除非商品行（例如税、合计、付款方式）。

**FR-CON-02：** 系统至少提供：蔬菜水果、肉/海鲜、乳制品/蛋、主食/烘焙、冷冻、零食、饮料、调味/烹饪、婴幼儿、清洁/家居、个人护理、宠物、酒类、其他、未分类。所有类别可由 Owner 重命名、隐藏或新增；既有历史行保存类别版本/ID，不能因改名而丢失。

**FR-CON-03：** 用户每次纠正“原始商品文本 → 显示名称 / 类别 / 规格”时，可选择“今后对本家庭相同文本采用此规则”。规则按家庭隔离，并显示命中来源；用户可在设置中编辑、停用或删除规则。

**FR-CON-04：** 用户可把多个别名合并为一个家庭自定义商品（Canonical Product），也可随时拆分。合并/拆分后，历史统计实时重算并保留审计记录。

**FR-CON-05：** 只有当收据头部、需要统计的行项目和总额校验均得到用户明确确认时，状态可由 `draft` 变为 `confirmed`。用户可保存草稿；草稿、被删除和有冲突的行不得计入任何正式统计。

### 4.3 金额与总额校验

**FR-MON-01：** 金额以整数分（cents）保存，币种默认 NZD；展示时本地化为 `$12.34`。禁止使用浮点数作为账本金额真值。

**FR-MON-02：** 系统计算 `商品行价合计 + 允许的调整项 = 收据总额`。差异在可配置的很小容差内可提示确认；超出容差时明确标红，用户必须选择折扣、退款、税费、非商品费用或手动修正其中一种调整原因后才能确认。调整原因可附备注，但备注不是确认前置条件。

**FR-MON-03：** 多买折扣、会员价、优惠券、退款和免费商品必须有独立标记。默认将受这些标记影响的单品价格标为“可能不可比”，但仍计入家庭实际支出。

### 4.4 支出查询与统计

**FR-ANA-01：** 已登录家庭成员可选择任意开始和结束日期，查看：总支出、收据数、已确认商品行数、按类别金额/占比、按商品金额/次数、按门店金额/次数。

**FR-ANA-02：** 所有统计至少支持日期、门店、类别、上传成员和“仅已确认”筛选；筛选条件在 URL/可分享的家庭内链接中保留。默认范围为本月，日期以家庭时区计算。

**FR-ANA-03：** 每个图表和汇总数字都可下钻到构成它的收据行；下钻结果显示门店、日期、规格、实付价、促销/可比标记与最后修改人。

**FR-ANA-04：** 未分类、无价格、被排除或可能重复的行必须分别计数并显示。系统不得把缺失值当成零，也不得将未分类行隐藏以抬高某类别比例。

**FR-ANA-05：** 分析页提供一个通用的“聚合视图”。用户可任意组合筛选条件：日期范围、一个或多个门店、一个或多个类别、一个或多个商品、上传成员、促销/可比状态；可选择按商品、类别、门店或时间（天/周/月）分组。第一版每个视图只允许一个主分组，避免难以理解的交叉表，但所有维度均可作为筛选条件。

**FR-ANA-06：** 对任何聚合视图，用户可选择指标：总实付金额、购买次数、收据数、购买数量（仅数量单位一致时）、平均每次实付金额、最低/最近/中位购买价（仅商品价格视图）。结果可按指标升序/降序排序，默认按总实付金额降序；显示名次、金额、占总额比例、样本数和可下钻的行项目。

**FR-ANA-07：** “商品花费排名”是聚合视图的预设：用户先选择任意日期范围及可选门店/类别筛选，再按家庭自定义商品分组、按总实付金额降序排列。未合并的别名不能静默混入同一个排名项目；页面必须提示用户可合并别名以得到完整历史。

**FR-ANA-08：** “门店花费”是聚合视图的预设：用户按门店分组，查看任意时间段内的总花费、收据数、商品行数、平均每张收据金额，以及按类别或商品下钻。门店名称来自用户确认或手动选择；无法可靠识别的门店归入“未确认门店”，不得被自动归到某连锁店。

### 4.5 商品搜索与家庭跨店历史价格

**FR-PRI-01：** 用户可按家庭自定义商品、别名或原始小票文本搜索。结果按精确商品、别名匹配、文本模糊匹配分组；歧义时要求用户选择，不自动把不同商品混为一谈。

**FR-PRI-02：** 商品详情默认展示全部历史，用户也可指定任意时间范围、一个/多个门店和可比性状态；页面显示每一次购买的日期、门店、数量/规格、实付价、促销标记，以及每个实际购买门店的购买次数、最近实付价/日期、最低实付价/日期、中位实付价、样本数和价格时间线。所有措辞必须为“本家庭历史购买价”，不称为零售商当前价、原价或市场最低价。

**FR-PRI-03：** 只有商品、规格单位与数量可解析且可比较时，系统才计算单位价：例如 `$ / L`、`$ / kg`、`$ / 100 g`、`$ / item`。计算基数为 `购买数量 × 每件规格`；不同单位、规格未知、促销/退款影响的观测默认不进入可比单位价集合，并给出原因。

**FR-PRI-04：** 跨店表必须显示资料边界：筛选日期、门店、样本数、可比/不可比条目数及“仅来自本家庭已确认小票”。样本少于 2 时不生成趋势或省钱结论。

**FR-PRI-05：** 用户可查看某一次购买相对本家庭同商品、同规格、同门店或跨门店可比历史中位价的差异；系统显示计算窗口与样本数，不将差异归因为某个超市“涨价”或“欺骗”。

### 4.6 洞察、节约提示和购买结构提示

**FR-INS-01：** 洞察必须是可选功能；第一次开启前说明资料范围、数据覆盖率与非医疗边界。每条洞察须展示“依据数据”“时间范围”“样本数”“算法规则”和关闭/反馈入口。

**FR-INS-02：** MVP 可生成以下确定性节约提示：

- 某自定义商品本次可比实付价高于本家庭指定窗口的中位价，且样本数不少于 3；
- 某类别在本月超过用户设置的家庭预算；
- 某类别本月支出高于此前三个月平均值，且金额及百分比变化均超过用户设置的阈值；
- 某商品在两个以上实际购买门店有足够可比历史样本，展示历史区间，不推荐“现在去某店买”。

**FR-INS-03：** MVP 可生成以下中性购买结构提示：确认食品行中各大类的金额/次数占比、未分类率、已确认率、含糖饮料/零食等用户自行启用类别的金额占比。所有界面必须写明“购买记录不等于实际食用，不能代表个人健康”。

**FR-INS-04：** 禁止输出疾病风险、营养缺乏、体重管理、儿童/孕期/过敏/药物、治疗或个性化饮食建议；禁止仅凭小票给商品“健康/不健康”分数。营养评分需在未来取得可靠产品营养资料、明确产品范围与专业审查后另立需求。

### 4.7 导出、删除与审计

**FR-DAT-01：** Owner 可导出家庭已确认收据、商品、分类和价格观测的 CSV；导出不应包含原始图片 URL、支付信息或 AI 内部提示。准备完成后采用短期有效、访问受控的下载链接。

**FR-DAT-02：** 用户可删除原图、整张收据或家庭。删除整张收据后应从统计、价格和洞察中移除。Owner 在删除家庭前必须输入家庭名称或完成同等强度二次确认；删除范围和不可恢复性需明确说明。

**FR-DAT-03：** 对确认、编辑、合并、拆分、导出、邀请和删除记录时间、操作者、对象和变更摘要；审计日志不记录原图内容、完整商品文本或支付信息。

## 5. 数据模型与状态机

### 5.1 最小实体

| 实体 | 关键字段 | 规则 |
| --- | --- | --- |
| Household | id、名称、时区、owner_id | 所有数据必须带 household_id。 |
| Member | user_id、household_id、role、状态 | 不允许跨家庭读取。 |
| Receipt | 状态、store_id/name、日期、total_cents、currency、creator | `draft / processing / needs_review / confirmed / deleted`。 |
| ReceiptImage | 存储键、哈希、上传时间、删除时间 | 私有访问；删除后不可再生成链接。 |
| ExtractionCandidate | 字段、候选值、原始文本、置信度、模型版本 | 永不作为统计输入。 |
| ReceiptLine | 显示名、原始文本、qty、规格、line_cents、category_id、状态 | 只有 confirmed receipt 的有效行可统计。 |
| CanonicalProduct / AliasRule | 家庭商品、别名、匹配方式、启用状态 | 仅影响本家庭。 |
| PriceObservation | line_id、store、日期、规格、单位价、可比性原因 | 从确认行派生，可重建。 |
| Budget / Insight | 类别/商品范围、周期、金额阈值、计算版本、依据快照 | 洞察可重算且可关闭。 |
| AuditEvent | actor、动作、对象、摘要、时间 | 用于可追溯，不泄漏内容。 |

### 5.2 状态转换

```text
上传 → processing → needs_review → confirmed
                      ↘ draft（用户继续手动编辑）
任意非 deleted 状态 → deleted
confirmed → needs_review（编辑影响金额、类别、商品合并或可比性时） → confirmed
```

确认操作需原子性地写入收据、有效行、价格观测与聚合失效事件。任何一步失败时不应出现“已入账但无行项目”或“价格已更新但收据未确认”的半完成数据。

## 6. 非功能需求

### 6.1 隐私与安全

- 最小化收集：不要求银行卡、会员号、病史、过敏、体重、孕期或药物资料；确认界面提示用户裁切/遮蔽不必要的会员或支付识别号。
- 授权：所有 API 在服务端验证登录身份、家庭成员关系和角色；不得仅凭客户端传入的 household_id 授权。
- 存储：原图与导出文件使用私有对象存储、加密传输；访问链接短期有效；日志中禁止记录原图、OCR 全文或令牌。
- AI：向外部模型服务发送前必须记录供应商、用途和保留政策；默认不得授权训练。服务不可用时回退手动流程。
- 数据删除：删除请求有明确完成状态；备份保留期限与恢复能力需在隐私说明中写明，不能承诺即时擦除无法即时擦除的备份。

### 6.2 性能、可靠性与可访问性

- 上传后应立即给出处理状态；同步页面不因 OCR 阻塞。网络中断时自动保留草稿，恢复后可继续。
- 首页/分析页展示缓存或上次更新时间，异步聚合延迟时不得静默给出不完整结果。
- 图表必须有等价数据表；颜色不能是唯一信息通道；所有表单可键盘操作，有标签、错误摘要与焦点管理。
- 移动端主要操作目标至少约 44×44 CSS px；长小票确认支持分段保存与虚拟列表，不丢失已编辑数据。
- 以应用可观察性记录匿名技术事件：上传失败率、OCR 失败率、确认完成率、聚合错误率和页面性能；不得把商品文本作为分析事件属性。

## 7. 验收标准与测试矩阵

| 编号 | 场景 | 验收结果 |
| --- | --- | --- |
| AC-01 | OCR 正确读出一张小票 | 用户仍须逐行确认；确认前首页金额不变。 |
| AC-02 | OCR 失败 | 用户无需刷新即可手动完成收据；最终统计正确。 |
| AC-03 | 行价合计与总额差 $2 | 确认按钮阻止或要求写明调整项；没有静默入账。 |
| AC-04 | 两家店购买同规格商品 | 商品页显示各店样本、日期、最近/最低/中位价与数据边界。 |
| AC-05 | 500g 与 1kg 商品 | 不直接比较行价；规格可解析时显示单位价与计算单位。 |
| AC-06 | 多买折扣商品 | 实际支出计入；价格观测标为可能不可比，默认不进单位价比较。 |
| AC-07 | 合并两个别名后拆分 | 历史金额、搜索与价格曲线正确重算，并有审计记录。 |
| AC-08 | 无任何确认收据的新家庭 | 显示引导空态，不显示 $0 的误导性趋势或健康结论。 |
| AC-09 | 成员尝试读取另一家庭的 URL | 服务端返回拒绝；不泄漏收据存在性或元数据。 |
| AC-10 | 删除一张已确认收据 | 下钻、总额、商品价格和洞察均移除该数据。 |
| AC-11 | 健康/节约洞察 | 显示算法、窗口、样本和覆盖率；无医学措辞。 |
| AC-12 | 时间范围与家庭时区边界 | 月初/月末收据进入正确范围，筛选与导出一致。 |
| AC-13 | 任意范围商品排名 | 给定日期、类别和门店筛选后，商品按总实付金额正确降序；每项金额、占比、样本数可下钻。 |
| AC-14 | 商品全部历史与按店筛选 | 默认列出该家庭商品的所有确认购买；选中一个门店和日期范围后，列表、汇总及价格曲线同步且不混入其他店数据。 |

测试层级：单元测试覆盖金额、单位价、可比性、日期窗口、类别占比；集成测试覆盖授权、状态转换、确认原子性与删除重算；端到端测试覆盖“上传/手动回退 → 确认 → 商品跨店对比 → 删除”；使用合成或获授权且已脱敏的小票作为测试夹具。

## 8. 发布切片与完成定义

### 切片 A：先让一家人可靠记账（第 1–2 周）

登录/单家庭、手动收据、类别、确认、日期与类别支出、私有数据库、删除和基本测试。没有 AI 也必须可日常使用。

### 切片 B：减少输入负担（第 3 周）

上传原图、异步 OCR/AI 候选、确认页、低置信度/失败回退、别名规则、总额和重复校验。

### 切片 C：把积累的数据变得有用（第 4 周）

商品搜索、家庭跨店历史价、单位价、可比性标签、下钻、预算与确定性节约/购买结构提示。

### 切片 D：可交付质量（第 5 周）

成员邀请、CSV、审计、可访问性、移动体验、E2E、错误监测、隐私说明和小规模家庭试用。

**MVP 完成定义：** 家庭能独立完成至少 10 张不同小票的录入；所有已确认金额可追溯；AI 失败不阻断；跨店价格不误称市场数据；删除能从所有聚合中生效；没有 P0/P1 授权、金额或隐私缺陷。

## 10. 十轮自审与优化记录

| 轮次 | 审查焦点 | 发现的问题 | 本版优化结果 |
| ---: | --- | --- | --- |
| 1 | 目标清晰度 | 初始想法把记账、比价、健康混在一起 | 固定核心问题、MVP 边界与四个可回答问题。 |
| 2 | AI 可靠性 | 自动入账会将 OCR 错误放大 | 明确候选/确认状态、置信度、手动回退和原子确认。 |
| 3 | 金额正确性 | 折扣、退款与总额不符会损坏账本 | 定义分单位存储、总额校验、调整项与不可比标记。 |
| 4 | 商品比较 | 同名异规格和促销价容易误导 | 引入家庭商品、别名、规格、单位价与可比性规则。 |
| 5 | “跨超市”措辞 | 易被理解为实时市场比价 | 全部限定为本家庭历史实付价，显示样本、日期和来源边界。 |
| 6 | 健康风险 | 小票不能证明实际饮食或健康 | 改为可关闭的购买结构提示，列出明确禁止内容。 |
| 7 | 隐私与权限 | 小票和家庭消费有敏感性；成员修改共享历史的权限不清楚 | 增加私有原图、服务端授权、导出/删除、AI 数据边界与审计；限定 Owner 处理影响全家的商品合并。 |
| 8 | 异常与空态 | 只描述理想成功流程 | 覆盖模糊、失败、离线、重复、无数据、筛选无结果与删除。 |
| 9 | 可验证性 | 功能描述无法判断完成 | 补充 12 个验收场景和单元/集成/E2E 测试分层。 |
| 10 | 可执行性 | 功能过多可能拖慢家庭首用 | 划分 A–D 发布切片、完成定义和后续功能进入门槛。 |
| 11（补充） | 数据聚合表达 | 原需求中的查询维度未明确组合、排序与排名规则 | 增加通用聚合视图、商品/门店预设、指标与排序规则，以及对应验收场景。 |

## 11. 仍待真实使用验证的假设

- 家庭愿意在每张小票上花约 30–60 秒确认，而不是仅看自动结果。
- 自动分类和“记住我的改法”能明显降低第二周后的录入成本。
- 家庭历史跨店价格比“全市场实时价格”更能满足首批用户的决策需求。
- 用户认为覆盖率、样本数和“可能不可比”的说明足够清楚，不会把提示理解成保证。

首周试用建议记录：每张收据的确认时长、被修正字段数、用户是否再次上传、最常查看的筛选维度，以及任何被误解的洞察文案。以这些观察决定下一轮产品调整，而不是先扩大范围。
